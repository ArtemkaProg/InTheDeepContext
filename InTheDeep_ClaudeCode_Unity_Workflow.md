# InTheDeep --- план розробки з Claude Code, Unity 6 та Unity CLI

> **Призначення документа:** це довгостроковий план організації розробки
> InTheDeep за допомогою AI. Не потрібно виконувати всі кроки зараз.
> Коли почнеться активна розробка, проходь розділи послідовно й
> перевіряй актуальність команд за офіційною документацією.
>
> **Цілі:** баланс вартості, швидкості та якості; мінімізувати
> непотрібне використання контексту; уникати повторної роботи;
> автоматично перевіряти код; зберегти контроль над архітектурою та
> ігровим задумом.

## 0. Короткий план

Основний стек:

-   **Claude Code Pro або Max** --- головний AI-агент для аналізу
    репозиторію, написання коду, тестування та виправлення помилок.
-   **Unity 6** --- рушій гри, сцени, префаби, фізика, матеріали,
    анімації та фінальна візуальна перевірка.
-   **Unity CLI** --- запуск доступних команд Unity з термінала:
    перевірки, тести, збірки та інші підтримувані операції.
-   **Unity skills / Unity Pipeline** --- готові засоби інтеграції
    Claude Code з Unity та автоматизації Editor, якщо вони сумісні з
    установленими версіями.
-   **Git** --- історія змін, гілки, перегляд diff і можливість
    повернутися до робочого стану.
-   **Unity Test Framework** --- автоматичні Edit Mode та Play Mode
    тести.
-   **За потреби пізніше:** GitHub Actions/CI, додаткові skills та Unity
    Accelerator.

Початковий принцип: **спочатку мінімальний робочий процес, потім
автоматизація**. Не починати з власного MCP-сервера, багатьох агентів,
платних додаткових сервісів чи складного CI, поки немає конкретної
проблеми, яку вони вирішують.

### Пріоритети

1.  Створити відтворюване середовище Unity та Claude Code.
2.  Написати короткий `CLAUDE.md` і базові документи про гру.
3.  Налаштувати Git і тести.
4.  Реалізувати маленький наскрізний прототип.
5.  Перевірити, чи працює цикл «завдання → код → тест → diff → commit».
6.  Виміряти реальні витрати й лише тоді оптимізувати або розширювати
    інструменти.

## 1. Вибір підписки Claude

### Початкова рекомендація

Почати з **Claude Pro**, якщо його лімітів достатньо для регулярної
розробки. Не купувати Max наперед лише через очікування, що проєкт буде
великим.

-   **Pro:** початковий варіант для налаштування, документації та
    прототипу.
-   **Max:** розглянути, якщо ліміти регулярно переривають роботу та
    створюють помітні втрати часу.
-   **API:** не вмикати додаткову оплату автоматично. Використовувати
    лише за наявності конкретної потреби й розуміння вартості.

Claude Code та звичайний Claude можуть використовувати спільні ліміти
облікового запису. Перевір актуальні умови підписки перед оплатою,
оскільки тарифи та ліміти можуть змінюватися.

### Контроль білінгу

-   Перевіряти `/status` у Claude Code.
-   За потреби використовувати `claude --version` і `claude doctor`.
-   Перевірити, чи не задано `ANTHROPIC_API_KEY` у середовищі, якщо
    хочеш користуватися саме включеним у підписку використанням.
-   Не оцінювати ефективність лише за довжиною відповіді. Дивитися на
    кількість завершених, перевірених завдань, кількість переробок і
    використання лімітів.

https://code.claude.com/docs/en/overview - Claude plans/pricing:

## 2. Налаштування середовища

### 2.1. Unity 6

1.  Встановити потрібну версію Unity 6 через Unity Hub.
2.  Створити проєкт і відкрити його в Editor.
3.  Зафіксувати точну версію Editor, яку використовує проєкт.
4.  Переконатися, що проєкт відкривається без помилок компіляції.
5.  Не оновлювати Unity посеред важливої задачі без потреби. Перед
    оновленням зробити Git-коміт або іншу резервну копію.

### 2.2. Unity CLI

Офіційна сторінка встановлення:
https://docs.unity.com/en-us/unity-cli/use-unity-cli

У документації можуть бути такі команди встановлення.

**Windows PowerShell:**

``` powershell
irm https://unity.com/install.ps1 | iex
```

**macOS/Linux:**

``` bash
curl -fsSL https://unity.com/install.sh | bash
```

Запуск скрипта з інтернету виконуй лише після перевірки офіційного
джерела та його інструкцій.

Після встановлення перевір:

``` bash
unity --version
unity --help
unity editors
```

Важливо: - CLI може бути експериментальним, а команди й параметри можуть
змінюватися. - Перед використанням конкретної команди перевір
`unity <command> --help` і документацію саме встановленої версії. -
Запиши версії Unity Editor та CLI в нотатках про середовище. - Не копіюй
команди зі старої інструкції, якщо актуальний CLI показує інший
синтаксис.

### 2.3. Claude Code

Встановити Claude Code за офіційною інструкцією:
https://code.claude.com/docs/en/overview

Перевірити:

``` bash
claude --version
claude doctor
claude
```

Усередині Claude Code:

``` text
/status
```

Переконатися, що активний правильний обліковий запис і очікуваний спосіб
оплати.

### 2.4. Інтеграція Unity з Claude Code

Спочатку перевір актуальні інструкції Unity:
https://docs.unity.com/en-us/unity-cli/use-unity-cli

У відповідних версіях CLI може бути доступне налаштування
Unity-плагіна/skills командою:

``` bash
unity setup claude
```

Не вважати команду гарантованою для кожної версії. Якщо вона не
розпізнається: 1. Перевір `unity --help`. 2. Відкрий актуальну
документацію Unity CLI. 3. Перевір, чи встановлено офіційні Unity skills
для Claude Code іншим способом. 4. Не створюй власну інтеграцію, доки не
з'ясуєш, що вже доступні засоби не покривають задачу.

### 2.5. Unity Pipeline

Unity Pipeline може надавати автоматизацію операцій усередині запущеного
Editor. Його можливості, вимоги й команди треба перевірити в
документації встановленої версії.

Якщо підтримується, документація може передбачати команди на кшталт:

``` bash
unity auth login
unity pipeline install
```

Після встановлення перевір:

``` bash
unity pipeline --help
unity commands
```

Не припускай, що всі ці команди доступні в кожній версії. Перевір їх
перед використанням.

Розділяй відповідальність: - **Claude Code:** вирішує, що потрібно
змінити, аналізує код і формує команди. - **Unity CLI:** запускає
підтримувані операції з командного рядка. - **Unity Pipeline:** виконує
підтримувані операції в контексті Editor. - **Unity Editor:** потрібен
для візуальної перевірки сцен, префабів, освітлення, фізики та
поведінки, яку не можна надійно оцінити лише за логами.

                                      прогресія, досвід гравця.

  `TECHNICAL_DESIGN.md`               Архітектура C#, межі систем,
                                      залежності, правила інтеграції з
                                      Unity.

  `LEVEL_GENERATION.md`               Правила генерації, кімнати,
                                      з'єднання, валідність і прохідність
                                      рівнів.

  `DECISIONS.md`                      Важливі рішення, причина вибору та

  `ROADMAP.md`                        Поточний етап, найближчі завдання
                                      та критерії готовності.

  `SESSION_STATE.md`                  Тимчасовий handoff для великої

### Правило підтримки документації

-   Документація описує задум, обмеження та рішення, які важко вивести з
    коду.
-   Код є джерелом істини для фактичної реалізації.
-   Не дублювати в документації всі поля й методи класів.
-   Оновлювати документи, якщо змінилися правила або архітектура.
-   Не передавати Claude всі документи щоразу. Читати лише ті, що
    потрібні для поточного завдання.

## 4. Базовий `CLAUDE.md`

Створи `CLAUDE.md` у корені репозиторію. Тримай його коротким: це
постійні правила, а не повна документація гри.

``` markdown
# InTheDeep — Claude Code Instructions

## Project
- Unity 6 game developed in C#.
- `Docs/VISION.md` defines the project vision.
- `Docs/GAME_DESIGN.md` defines gameplay requirements.
- `Docs/TECHNICAL_DESIGN.md` defines architecture when present.
- `Docs/ROADMAP.md` tracks current priorities.

## Working Rules
- Inspect relevant code and documentation before editing.
- Prefer the smallest complete change.
- Do not rewrite unrelated systems.
- Follow existing project conventions.
- Do not add packages or external dependencies without approval.
- Ask before making irreversible changes or deleting project assets.
- Do not silently change established gameplay requirements.
- Keep documentation consistent with implemented behavior.

## Workflow
1. Identify the requirement and relevant files.
2. Make a short plan for non-trivial tasks.
3. Implement the change.
4. Run relevant tests and compilation/build checks.
5. Inspect the diff and report the result.
6. Report any checks that could not be completed.

## Validation
- Use the repository's documented Unity CLI commands.
- Never claim a test, compilation or build passed unless it ran successfully.
- Distinguish test failures from infrastructure failures.
- Do not repeatedly retry deterministic failures without changing the cause.

## Reporting
- Summarize changed files and behavior.
- Include test commands and their actual results.
- List unresolved issues and assumptions.
- Keep the final report concise.
```

Після появи конкретних правил C# чи тестування їх можна винести в
`.claude/rules/`. Не перенось туди загальні відомості про гру, які
потрібні лише для окремих завдань.

## 5. Оптимізація контексту й сесій Claude Code

### Основне правило

**Не намагайся зробити кожен запит максимально коротким ціною втрати
ясності. Зменшуй зайву інформацію, повторну роботу та невизначеність.**

Довга документація може економити час і токени в довгостроковій
перспективі, якщо вона запобігає помилкам. Але завантажувати всі
документи в кожну сесію теж не потрібно.

### Три типи сесій

**A. Дослідження/планування** - Для нової системи або складного
архітектурного питання. - Результат: короткий план, ризики, рішення та
критерії готовності. - Не просити в цій самій сесії реалізувати весь
проєкт, якщо план великий.

**B. Реалізація** - Одна логічно завершена функція. - Claude читає лише
потрібні документи й файли, вносить мінімальні зміни та запускає
відповідні тести. - Завершити коротким звітом і переглядом diff.

**C. Діагностика** - Для дефекту, який не вдалося виправити в звичайній
сесії. - Надати точний лог, очікувану й фактичну поведінку, кроки
відтворення та найменший релевантний фрагмент коду. - Не передавати всю
історію розробки, якщо вона не потрібна.

### `/clear` та `/compact`

-   `/clear`: використовувати, коли попередня задача завершена й
    наступна незалежна.
-   `/compact`: використовувати, коли поточна задача триває, але історія
    стала великою.
-   Не запускати ці команди механічно за таймером. Вибирати за станом
    роботи.
-   Перед завершенням великої незавершеної задачі створити короткий
    handoff у `Docs/SESSION_STATE.md`.

### Шаблон handoff

``` markdown
# Session State

## Goal
Що саме треба завершити.

## Completed
Що вже реалізовано.

## Changed Files
Які файли змінено і навіщо.

## Validation
Які команди запускалися та які результати отримано.

## Remaining
Що не завершено, які є помилки або ризики.

## Next Action
Одна конкретна наступна дія.
```

Не зберігати `SESSION_STATE.md` як постійний журнал кожного
повідомлення. Після завершення задачі перенести важливі рішення до
відповідної документації, а тимчасовий handoff очистити або видалити.

### Важливі практики економії

-   Не просити виводити весь код файлів у відповідь, якщо він уже
    збережений у репозиторії.
-   Просити короткий звіт: змінені файли, тести, проблеми, наступний
    крок.
-   Не просити повний аналіз усієї архітектури для зміни однієї функції.
-   Не запускати багато subagents за замовчуванням. Вони корисні для
    незалежних задач, але також споживають ресурси.
-   Не змушувати Claude повторювати один і той самий тест без зміни
    причини збою.
-   Зберігати стабільні рішення в документації, а не повторювати їх у
    кожному запиті.
-   Для складних завдань просити короткий план перед редагуванням; для
    очевидних дрібних змін не створювати зайву бюрократію.

## 6. Стандартний цикл розробки

Для більшості функцій використовувати цикл:

1.  **Завдання:** чітко сформулювати потрібну поведінку й критерії
    готовності.
2.  **Контекст:** Claude перевіряє відповідну документацію та лише
    потрібні файли.
3.  **План:** короткий план для нетривіальних змін.
4.  **Реалізація:** найменша завершена зміна, без переписування не
    пов'язаних систем.
5.  **Перевірка:** відповідні тести та потрібні перевірки
    компіляції/збірки.
6.  **Аналіз:** переглянути diff, переконатися, що немає випадкових
    змін.
7.  **Фіксація:** Git-коміт після успішної перевірки.
8.  **Документація:** оновити лише ті документи, які справді змінилися
    за змістом.

### Шаблон запиту для Claude Code

``` text
Implement: [specific feature]

Goal:
[Expected behavior]

Acceptance criteria:
- [Criterion 1]
- [Criterion 2]
- [Criterion 3]

Constraints:
- Read only the relevant documentation and code first.
- Make the smallest complete change.
- Do not modify unrelated systems.
- Do not add dependencies without approval.

Validation:
- Run the relevant Unity tests using the documented CLI commands.
- Report exact commands and actual results.
- Distinguish test failures from environment or infrastructure failures.

Finish with:
- Changed files and why.
- Test/build results.
- Remaining risks or unresolved issues.
```

Для маленької задачі скоротити цей шаблон до кількох речень. Не потрібно
копіювати повну інструкцію щоразу, якщо вона вже є в `CLAUDE.md` або
skill.

## 7. Unity CLI та автоматичні перевірки

### Два рівні перевірок

**Швидкий рівень --- після невеликої зміни** - Переглянути diff. -
Запустити релевантні Edit Mode тести. - Перевірити помилки компіляції та
результати тестів. - Для змін, залежних від сцени, фізики чи реального
ігрового циклу, додати Play Mode тести або ручну перевірку.

**Повний рівень --- перед завершенням функції або контрольним етапом** -
Edit Mode тести. - Play Mode тести, якщо вони потрібні. - Збірка
цільової платформи. - Перевірка логу, артефактів та diff.

### Приклади команд

Нижче наведено приклади синтаксису Unity CLI. Перед використанням
перевір доступність і параметри в установленій версії через
`unity --help` або `unity <command> --help`.

Edit Mode:

``` bash
unity test . \
  --mode EditMode \
  --report-format junit \
  --output ./test-results/editmode.xml \
  --timeout 600
```

Play Mode:

``` bash
unity test . \
  --mode PlayMode \
  --report-format junit \
  --output ./test-results/playmode.xml \
  --timeout 600
```

Приклад збірки для Windows:

``` bash
unity build . \
  --target StandaloneWindows64 \
  --output-path Build/InTheDeep.exe \
  --timeout 900
```

Це приклади, а не гарантія сумісності з кожною версією CLI. Якщо
параметри відрізняються, використовувати актуальну документацію й
`--help`. Переконатися, що каталоги для звітів існують або створюються
скриптом.

### Як обробляти невдалі тести

Розрізняти: - Тест запустився, але перевірка не пройшла. - Тестовий
процес не запустився або завершився помилкою середовища. - Процес
перевищив тайм-аут. - Компіляція не пройшла.

Рекомендоване правило: 1. Перша спроба --- отримати точну помилку й
локалізувати причину. 2. Друга --- внести обґрунтоване виправлення. 3.
Повторно запустити відповідну перевірку. 4. Якщо проблема залишилася,
припинити сліпі повтори й повідомити точну причину/блокер.

Не запускай повну збірку після кожного косметичного редагування. Не
запускай паралельно кілька процесів, що конфліктують за той самий Unity
Editor або файли проєкту.

## 8. Skills та hooks

### Почати з двох skills

**`.claude/skills/implement-feature/SKILL.md`** - Прочитати потрібну
документацію. - Знайти релевантні класи. - Перевірити поточну
архітектуру. - Реалізувати мінімальну завершену зміну. - Запустити
відповідні тести. - Підсумувати diff і результати.

**`.claude/skills/validate-project/SKILL.md`** - Перевірити Git status і
diff. - Визначити потрібний рівень тестування. - Запустити доступні
перевірки. - Зібрати результати й помилки. - Не оголошувати успіх, якщо
команда не виконалася. - Видати короткий звіт.

Skills --- це повторно використовувані процедури, які можна викликати за
потреби. Не перетворювати кожну дрібну дію на окремий skill.

### Hooks

Додавати hooks лише для механічних, передбачуваних дій, наприклад: -
перевірки форматування; - попередження про небезпечні операції; -
перевірки випадкових змін у великих файлах; - запуску швидких перевірок,
якщо це не створює затримок.

Не запускати повну Unity-збірку після кожного редагування. Спочатку
переконатися, що hook справді економить час і ресурси.

## 9. Git workflow

Використовувати просту модель: `main` + окрема гілка для кожної логічної
функції.

Приклади: - `feature/room-generation` - `feature/programming-system` -
`fix/invalid-levels`

Типовий процес:

``` bash
git switch -c feature/room-generation

# Claude implements and validates the feature.

git status
git diff
git add <specific-files>
git commit -m "Implement room generation"
```

Перед `git add` перевіряти список змінених файлів. Не додавати все
автоматично, не переглянувши diff.

### Unity `.gitignore`

Використовувати офіційний Unity template:
https://github.com/github/gitignore/blob/main/Unity.gitignore

Зазвичай не комітити: - `Library/` - `Temp/` - `Logs/` - `Obj/` -
локальні файли IDE - тимчасові build-артефакти, якщо команда не вирішила
зберігати їх окремо

Не ігнорувати файли, потрібні для відтворення проєкту, зокрема: -
`Assets/` - `Packages/manifest.json` - `Packages/packages-lock.json` -
`ProjectSettings/`

Для великих бінарних ресурсів розглянути Git LFS лише тоді, коли розмір
і характер ресурсів цього вимагають.

### GitHub та CI

На старті достатньо локального Git. Після появи стабільних тестів можна
налаштувати GitHub Actions або іншу CI-систему для перевірок при
push/pull request.

Не починати зі складного багатоплатформного конвеєра. Спершу довести, що
проєкт стабільно перевіряється локально.
