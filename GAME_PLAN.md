# План розробки: гра в стилі Subnautica (Unity 6 + Blender + Claude Code)

> Нотатки на майбутнє. Основа: один статичний, ретельно спроєктований світ, який росте зона за зоною. ШІ (Claude Opus через Claude Code) допомагає скриптами й кодом, а не замість дизайну.
>
> **Позначка:** усе, що стосується конкретних інструментів (Unity CLI, BlenderMCP, ліміти планів), перевіряйте в актуальній документації перед початком. Вони швидко змінюються.
>
> **Існуючий прототип:** гра вже має робочий прототип «In The Deep» (HDRP). Усе про нього, що міняти, а що залишити, дивіться в **Додатку A** в кінці файлу.

## 1. Інструменти

### Claude Code
- Працює з папкою Unity-проєкту: читає й пише C#, запускає команди в терміналі.
- Основна модель для складного (архітектура, системи, важкі баги): Opus. Для рутини (прості скрипти, дрібні правки): дешевша модель, перемикання через `/model`.
- Ліміти спільні для чату й Claude Code. Великий проєкт з'їдає їх швидко, тому працюємо маленькими задачами.

### Unity CLI (офіційний, терміналний)
- Дає агенту керувати редактором із терміналу: команди редактора, eval C#-коду, тести, збірки, доступ до runtime.
- Станом на пошук був у бета-версії й працював разом з пакетом `com.unity.pipeline`.
- Не вантажить опис інструментів у контекст, як MCP, тому дешевше по токенах.
- **Перед використанням:** знайти офіційну документацію Unity, перевірити вимоги до версії редактора й поставити за їхньою інструкцією, а не зі сторонніх репозиторіїв.

### Blender з термінала (основний шлях)
```
blender -b -P script.py -- --zone reef_01
```
- `-b` запускає Blender без інтерфейсу, `-P` виконує Python-скрипт.
- Claude пише скрипт, запускає його, читає помилки й виправляє.
- Недолік: Claude не бачить результат. Рішення: скрипт може робити рендер-превʼю, яке ви дивитесь самі (або даєте агенту як картинку, коли це справді потрібно, бо це витрачає токени).

### Blender MCP (опційно, потім)
- Корисний для ітерацій у живій сесії («зроби скелю вище»).
- Опис інструментів займає контекст. Якість різних проєктів дуже різна, треба перевіряти, що живе й підтримується.
- Підключати, якщо відчуєте, що бракує візуального зворотного зв'язку.

### Фаза 1. Рішення про розбиття світу (до першої зони!)

## 3. Деталізація зони скриптами

Тут Claude найкорисніший. Процедурність працює **всередині вашого дизайну**:

- Правила розстановки коралів, водоростей, каміння, дрібної фауни за типом поверхні, глибиною, кутом нахилу.
- Кілька варіантів кожного ассета (різні seed, масштаб, поворот).
- Скрипти Blender для процедурних ассетів: скелі, кораловий ріст, сталактити.
- Інструменти в редакторі Unity: пензлі для розстановки, перегенерація зони за правилами.
- Автоматична оптимізація: LOD, спрощені колізійні меші, статичні батчі.

Принцип: **дизайнер вирішує, де і що має бути, а скрипт заповнює деталі**. Конкретні місця (входи в печери, ключові локації, «вау»-моменти) розставляються вручну.

## 4. Пайплайн Blender → Unity

### Структура репозиторію (приклад)
```
/Assets                 ← Unity
/BlenderSource
    /zones              ← .blend файли зон
    /props              ← ассети (скелі, кораловий ріст)
    /scripts            ← Python-скрипти генерації й експорту
/Docs                   ← нотатки, цей файл
CLAUDE.md
```

### Правила експорту
- Формат: FBX (звичний варіант) або glTF. Вибрати один і тримати.
- Blender має вісь Z вгору, Unity вісь Y вгору. Налаштувати осі експорту раз і закріпити в скрипті.
- Перед експортом: застосувати трансформації (scale/rotation), перевірити нормалі, прибрати зайве.
- Масштаб: 1 одиниця = 1 метр.
- Іменування: єдина схема (`zone01_cave_main`, `prop_rock_a_lod0`).
- **Автоматизувати експорт одним скриптом**, щоб він був відтворюваним (Claude його пише й підтримує).

### Колізії й LOD
- Для колізій не використовувати високополігональний меш: робити окремий спрощений колізійний меш.
- LOD для далеких шматків: або LOD-групи Unity, або окремі спрощені меші в тому ж експорті.

### Матеріали
- Для рельєфу краще triplanar-шейдер за біомом, ніж ручні UV на гігантських мешах.
- Матеріали зон узгодити із render pipeline.

## 5. Git і проєкт

- **Git LFS** для великих файлів: `.blend`, `.fbx`, `.png`, `.psd`, `.wav`, `.mp3`, `.ogg`, `.mp4`.
- `.gitignore` для Unity: `Library/`, `Temp/`, `Logs/`, `Obj/`, `UserSettings/`, `Builds/`.
- У Unity: Asset Serialization = Force Text, Meta Files = Visible Meta Files (щоб Git добре працював зі сценами).
- Коміт після кожного робочого кроку. Невеликі коміти дають можливість відкотитися, якщо Claude щось зламав.
- Гілка на кожну велику річ (зона, система).
- Бекап поза комп'ютером (хмара або другий диск). Git без віддаленого репозиторію не захищає від втрати диска.

## 6. Як працювати з Claude Code

### Принципи
- **Маленькі чіткі задачі:** «додай систему кисню з таким поведінкою», а не «зроби гру».
- Для великої задачі спершу просити план (режим планування), перевіряти його, і тільки потім код.
- Після кожної робочої зміни: перевірка у Unity, коміт.
- Нова задача, то нова сесія (економить токени й тримає контекст чистим).
- Не вантажити в чат великі файли без потреби.
- **Перевіряйте код.** Ви повинні розуміти, що відбувається в проєкті. Кому довіряти вибір архітектури, вирішуєте ви.
- Дизайн (як має виглядати й відчуватися) вирішуєте ви. Claude не відчуває, що «тут красиво» або «тут порожньо».

### Шаблон `CLAUDE.md` (покласти в корінь проєкту)
```markdown
# Проєкт: підводна гра (стиль Subnautica)

## Стек
Unity 6 (6000.0.58f2), C#, Blender (Python-скрипти), Git + LFS.
Контекст прототипу: Docs/InTheDeep_ProjectState_v10.md (частина застаріла: Terrain, версія Unity).

## Правила
- 1 одиниця = 1 метр.
- Світ статичний, поділений на зони (розмір зони: ___). Зони підвантажуються за відстанню.
- Render pipeline: ___ (у прототипі HDRP).
- Іменування: PascalCase для класів, camelCase для змінних, префікс зони в ассетів.
- Не змінювати файли поза папками Assets/ та BlenderSource/ без запиту.
- Перед великою зміною показати план.
- Після змін: переконатись, що проєкт компілюється (Unity CLI), перелічити змінені файли.

## Команди
- Експорт зони з Blender: `blender -b ... -P BlenderSource/scripts/export_zone.py -- --zone <name>`
- Перевірка компіляції: (команда Unity CLI)

## Поточний етап
(оновлювати вручну)
```

### Економія токенів
- Робота з файлами й CLI найдешевша. Скриншоти найдорожчі.
- Підключати тільки потрібні MCP/інструменти.
- `/clear` між несумісними задачами; стискати довгі сесії.
- Opus для складного, дешевша модель для рутини.

## 7. Звук, анімація, атмосфера

- **Звук дуже важливий для атмосфери.** Claude тут не допоможе генерацією. Потрібні бібліотеки звуків (ліцензії!), запис або окремі аудіогенератори. Продумати окремо: амбієнт біомів, звуки глибини й тиску, істоти, інтерфейс, музика.
- **Анімації:** Claude допоможе з Animator-контролерами й кодом, а самі кліпи краще брати з готових джерел або робити вручну. Для істот з нестандартною анатомією готових кліпів може не бути.
- **Атмосфера:** підводний туман, кавстики, частинки (морський сніг), освітлення по глибині. Налаштовується під обраний render pipeline.

## Додаток A. Існуючий прототип «In The Deep»

> Джерело: файл `InTheDeep_ProjectState_v10.md` (документ-контекст для Claude). Рекомендую покласти його в `Docs/` проєкту. Частина його вмісту (версія Unity, Terrain) після змін застаріє, тому оновлюйте або позначайте застаріле.

### A.1. Коротко про прототип
| | |
|---|---|
| Назва | In The Deep (Unity-проєкт називається Sabna2) |
| Жанр | Підводний психологічний хорор / виживання |
| Рушій | Unity 2022.3.56f1, HDRP (тепер міграція на Unity 6) |
| Мова | C# |
| Сеттінг | Планета-океан Kepler-22b. Корабель гравця розбився, довкола сліди тих, хто був тут раніше (бочки, гайки, уламки). Щось є в глибині, прямих відповідей гравець не отримує, тільки натяки. Стиль Dark Souls, але мінімалістично |
| Як зроблено | Світ у редакторі вручну, а архітектуру й скрипти писав Claude на безкоштовному плані |
| Статус | Робочий, але не ідеальний прототип |

- **Shallows** (зроблений): поверхня, бочки з маслом, гайки/шурупи, пісок.
- **Lowgrounds** (у процесі): темніше дно, каміння, водорості, металолом, печера.

Це готова відправна точка для вашого майбутнього рішення про біоми, але вона не обов'язкова.

### A.5. Що зміниться і що з цього випливає
**Terrain (Terrain1–9) буде видалено**, світ перейде на меші з Blender, розбиті на зони. Від Terrain залежать речі, які треба перевірити й переробити:

| Що залежить від Terrain / координат | Що з цим робити |
|---|---|
| `RockSpawner` і `SeaweedSpawner` (зона X=400–1500, Z=200–1150, виключена зона Shallows, «Max Terrain Y = 310») | Перевірити в коді, як вони визначають висоту (імовірно за Terrain). Переписати під raycast по колайдерах мешів і прив'язати до зон (кожна зона розставляє свої ассети у своїй сцені) |
| `DepthAtmosphere` (зашиті Y-значення: shallowY=3690, deepY=3650) | Зробити глибину відносною до поверхні води, а не абсолютними числами. Поверхню краще нормалізувати до Y=0 (глибина від'ємна), інакше при кожній зміні світу все ламається |
| Океан (Water Surface 1000×1000, Y=3712) і `WaterVolume` | Перевірити тип і межі водної поверхні для великого світу, узгодити з новими координатами |
| `SeagrassRenderer` (позиції генеруються на старті) | Перевірити, як визначає висоту. Прив'язати до зон |
| Одна велика сцена `OutdoorsScene` (гравець, UI, світло, світ разом) | Розділити на **постійну (core)** сцену (гравець, UI, світло, менеджери) і **сцени зон** (рельєф + ассети), які підвантажуються за відстанню |
| Синглтони (`Hotbar.Instance`, `PlayerSwimController.Instance`) | Нормально, якщо живуть у core-сцені. Перевірити, що вони не лежать у зонах |

Також: значення в налаштуваннях спавнерів (наприклад, «Max Terrain Y = 310»), можливо, застаріли після того, як океан і шкала глибини були зсунуті (3650–3712). Перевірити.

**Корисний факт:** печера в прототипі вже є звичайним мешем з triplanar-матеріалом. Це готовий невеликий тест для підходу «рельєф як меші»: можна на ній відпрацювати експорт, колізії й LOD ще до зон.

### A.6. Міграція Unity 2022.3 → Unity 6 (HDRP)
Робити строго в такому порядку:
1. **Закомітити прототип у Git** (з LFS) у поточному стані, і зробити додаткову копію папки проєкту.
2. Відкривати в Unity 6 лише на окремій гілці або копії.
3. Звіритися з офіційним посібником Unity щодо оновлення з 2022.3 LTS на Unity 6 (чи підтримується пряме оновлення і які кроки для HDRP).
4. Після відкриття: прочитати консоль (помилки, застарілі API), запустити HDRP Wizard і виправити його зауваження.
5. Перевірити **візуал**: Water Surface, об'ємний туман, Volume-профілі (`LowgroundsVolume`, `Sky and Fog Volume`), освітлення й експозицію, фейковий промінь ліхтарика. Це зазвичай змінюється найбільше.
6. Перевірити **керування**: скрипти використовують старий `Input` (`Input.GetMouseButtonDown` тощо). У Player Settings перевірте Active Input Handling (Input Manager або Both), інакше керування перестане працювати.
7. Перевірити матеріали сторонніх ассетів, `DrawMeshInstanced`-трава, колізії, LOD.
8. Запустити сцену, пройти основні механіки (плавання, інвентар, крафт, піч, турбіна), зафіксувати, що зламалось, і виправити.
9. Тільки після цього комітити результат міграції.

### A.8. Перший крок із Claude Code: аудит проєкту
Перш ніж розширювати, попросіть Claude Code (в окремій сесії, у режимі планування, без змін коду) зробити огляд:
- Описати архітектуру: які системи є, як вони пов'язані, де синглтони й жорсткі залежності.
- Знайти зашиті числа й координати (особливо Y, X/Z зон), які ламаються при зміні світу.
- Знайти потенційні проблеми продуктивності (Update з важкою логікою, пошук об'єктів кожен кадр тощо).
- Знайти місця, що залежать від Terrain.
- Запропонувати порядок рефакторингу, не виконуючи його.

Результат зберегти в `Docs/` і використати для `CLAUDE.md`. Це дасть вам розуміння власного проєкту, а не лише його роботу.

### A.9. Сторонні ассети й ліцензії
Прототип використовує готові ассети. Якщо плануєте публікувати чи продавати гру, **перевірте ліцензію кожного**:

- модель турбіни, згенерована в Meshy AI (перевірити умови використання для вашого плану),
- анімації Mixamo (для Monster Fish),
- будь-які інші ассети в проєкті.

Ведіть окремий файл-реєстр ассетів (назва, джерело, ліцензія, чи потрібна атрибуція).

### A.10. Як це лягає в загальний план
- Прототип це **готовий набір механік**, який економить місяці роботи над системами (фаза 4).
- Фази 1–3 (розбиття світу, вертикальний зріз, зони) все одно потрібні, бо саме світ у прототипі зміниться найбільше.
- Вертикальний зріз зручно робити, **замінивши частину Terrain** однією зоною з Blender і перевіривши, що гравець, спавнери й атмосфера працюють на новому рельєфі.
