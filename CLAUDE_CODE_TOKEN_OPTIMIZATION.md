# Claude Code — Token & Cache Efficiency (InTheDeep)

> Практичний довідник для розробки InTheDeep у Unity 6 через Claude Code + Unity CLI. Це **рекомендації для workflow**, а не нові рішення щодо геймплею. Перевіряй актуальні команди та ціни перед застосуванням.

## 1. Як працюють токени та prompt caching

API-запит може містити: новий вхід, **cache write** (запис придатного до повторного використання префікса), **cache read** (повторне використання вже кешованого префікса) і output (зокрема reasoning). Великі загальні підсумки token usage — **сума багатьох запитів**, а не розмір одного контекстного вікна.

- Висока частка cache read **сама по собі не означає неефективність**. Кешоване читання зазвичай значно дешевше за звичайний вхід.
- Не варто намагатися «прибрати cache read» ціною повторних повних завантажень. Оптимізуй **зайвий контекст, кількість безрезультатних звернень, повторні цикли й помилки кешування**.
- Зміни початку промпта/інструкцій або структури інструментів можуть зменшити ефективність повторного використання кешу.
- Показані в інструментах API-equivalent costs не обов'язково є фактичними платежами на Pro/Max. Ліміти підписки й можливе API-використання перевіряти окремо; не робити висновків лише за доларовим еквівалентом.

## 2. Головні правила для проєкту

1. **Одна логічна задача на сесію.** Планування нової складної системи → імплементація обмеженого зрізу → тести/діагностика. Не змішувати незалежні системи (інвентар, генерація океану, AI істот) в одному необмеженому контексті.
2. **Мінімальний, але достатній контекст.** Завантажити `CONTEXT.md`, `CLAUDE.md` і *лише релевантні* документи та C# файли. Не читати всі `Concepts/World/`, `Creatures/` і `Mechanics/` «про всяк випадок». Кожне рішення зберігати в одному основному документі.
3. **Короткий `CLAUDE.md`.** Правила роботи, перевірки, навігація по документах — не дублікати дизайну або журнали роботи.
4. **Стислий результат інструментів.** Логи Unity зберігати повністю локально, але повертати в контекст лише підсумок, перші релевантні compiler errors, stack trace потрібного збою та список failing tests. Повні логи читати на запит, коли стислого результату недостатньо. Не приховувати помилки чи значущі попередження.
5. **Обережні цикли перевірки.** Не повторювати ту саму команду з тією самою детермінованою помилкою без зміни причин. Спочатку релевантні тести/компіляція, ширші перевірки — перед інтеграцією.
6. **Вибирати модель/effort за складністю.** Високий reasoning для архітектури, нетривіальної генерації, багів між системами; стандартні компоненти, документація й нескладні тести — за можливості дешевшою моделлю/нижчим effort. Команди та доступні рівні перевіряти в поточній версії Claude Code.
7. **Subagents лише з чітким результатом.** Делегувати ізольований аудит, пошук або перевірку, отримувати стислий висновок. Кожен агент має власні витрати; паралелізм не гарантує економії.
8. **Між сесіями — handoff.** Для незавершеної задачі: мета, змінені файли, зроблено, перевірено, залишилося, наступна дія. Не переписувати всю історію; постійні рішення переносити в їхні authoritative documents.

## 3. Робочі команди Claude Code

- `/context` — дивитися розподіл поточного контексту.
- `/compact` — стискати довгу *актуальну* сесію, коли це доцільно; стиснення теж має вартість і може втрачати деталі.
- `/clear` — починати чистий контекст для нової незалежної задачі; початкова документація може завантажитися знову.
- `/status` — перевіряти режим використання/підписку; команди і поведінка можуть змінюватися.

**Не скидати або стискати контекст за жорстким таймером.** Рішення залежить від завдання й фактичного використання контексту.

## 4. Unity CLI — схема обмеження логів

1. Запускати перевірку і зберігати **повний** stdout/stderr та exit code у файлі.
2. Вивести: назву перевірки, exit code, кількість passed/failed/skipped тестів, релевантні compiler errors і кілька контекстних рядків.
3. Якщо збій незрозумілий — відкрити відповідну частину повного логу; не обрізати єдине пояснення помилки.
4. Не передавати в модель багатотисячні логи успішного виконання чи дублікати попереджень.

Це правило для майбутнього wrapper script; **не припускати**, що він уже реалізований. Конкретні команди залежать від версії Unity CLI / Unity Test Framework.

## 5. Як вимірювати ефект

На кількох порівнюваних задачах фіксувати:
- Модель, effort, кількість запитів/циклів та завершених задач.
- Input, cache creation, cache read, output/reasoning tokens (де доступно).
- Кількість повторних запусків тестів, тривалість і частоту переробок.
- API-equivalent cost **окремо** від реальних платежів і лімітів Pro/Max.

Оцінювати **вартість/ліміти на одну якісно завершену й перевірену задачу**, а не просто меншу кількість cache reads. Скорочення контексту може погіршити якість і спричинити додаткові запити.

## 6. Пріоритет впровадження

**Спочатку:** релевантні документи, короткі сесії з handoff, Unity log filtering, уникнення безрезультатних повторів.

**Після замірів:** налаштування effort/model routing, subagents, додаткова автоматизація й CI. Не будувати складний інструментарій лише заради економії токенів.
