# InTheDeep — речовини, контейнери й хімічні процеси (SYS-CHM)

> **Статус:** [Рішення] — погоджено 2026-11-13; [Пропозиція] — спосіб майбутньої реалізації; [Відкрито] — не визначено.
> **Суміжні системи:** [інвентар](../Inventory/INVENTORY_AND_LOGISTICS.md), [дослідження](../../Progression/RESEARCH_SYSTEM.md), [виробництво](../Construction/CONSTRUCTION_AND_MANUFACTURING.md).
> **Призначення для Claude Code:** цей файл є основним джерелом правил для представлення речовин, їхнього фізичного зберігання й доступної гравцеві хімії. Не трактувати приклади як зафіксовані рецепти.

## 1. Речовина ≠ предмет

**[Рішення]** Хімічна речовина — вміст із кількістю та потрібними характеристиками, а не абстрактний «предмет» у клітинках інвентарю. Фізичним об'єктом інвентарю може бути ємність із вмістом: пробірка, балон, каністра, спеціальна паливна касета тощо. Тверда сировина може існувати як фізичні шматки/руда/злитки, коли це відповідає її формі.

**[Рішення]** Різні речовини можуть використовувати спільні типи відповідних контейнерів; кожному газу чи рідині не потрібна унікальна 3D-модель предмета. Інтерфейс має показувати вміст, кількість і суттєві обмеження контейнера. Контейнери допускають повторне використання, переливання/перекачування в сумісне обладнання.

**[Рішення]** Лабораторна проба та промисловий запас — різні сутності за призначенням. Проба зберігає необхідну інформацію про походження/склад/умови відбору для аналізу; промисловий запас — насамперед придатну для виробництва кількість речовини. Не перетворювати кожну пробірку на умовну одиницю промислового ресурсу.

**[Рішення]** Враховувати фізичні вимоги до зберігання там, де вони мають ігровий сенс: тиск, герметичність, сумісність матеріалу, температура та безпека. **Не** створювати вручну окремий симулятор усіх властивостей для кожної речовини.

**[Приклад, не обов'язкова технологія]** Тритій — ізотоп водню, може зберігатися в спеціалізованій системі, а не як «кристал тритію» в інвентарі. Класи ємностей, конкретні матеріали й місткості не визначені.

## 2. Транспортування й автоматизація

**[Рішення]** На ранніх етапах гравець переносить відповідні ємності й передає їх вміст у обладнання. З розвитком інфраструктури виробничі машини можна забезпечувати речовинами через автоматизовані резервуари й трубопроводи/інший доречний транспорт, без постійного ручного перекладання контейнерів.

**[Пропозиція]** Для прототипу достатньо компактних характеристик сумісності контейнера/порту (тип речовини або клас середовища, припустимі умови, кількість). Не вимагати детальної симуляції кожної молекули, течії чи газової суміші.

## 3. Хімія має бути зрозумілою без попередніх знань

**[Рішення]** Ціль — гравець може вивчити хімічні принципи в самій грі, без пошуку інструкцій у Google й без знання рівнянь напам'ять. Основа — експерименти, наочні причинно-наслідкові зв'язки, зрозумілі вхідні речовини, спосіб обробки, умови та виходи; складність вводиться поступово. Реальна хімія — підґрунтя, але не іспит на хіміка.

**[Рішення]** Знання властивостей, відкриття процесів та їхнє інженерне застосування — пов'язані, але **різні кроки**:
1. Зразок / аналіз → корисні відомості про склад і властивості.
2. Вивчення придатних методів обробки → відкриття конкретного процесу та його умов.
3. Застосування відомих процесів, обладнання й доступної сировини для бажаного результату.

**[Рішення]** Дослідження речовини **не** відкриває автоматично всі рецепти, технології чи призначення цієї речовини. І навпаки, процес не повинен бути прихованим лише тому, що гравець не знає його реальної наукової назви: гра пояснює його функцію доступними засобами.

**[Рішення]** Гравець обирає осмислені методи й параметри, а не обов'язково вручну балансує всі формули/молі/концентрації. Не перетворювати хімію на обов'язкову серію однакових мініігор; коли спосіб перевірено, гравець може повторювати й автоматизувати його без нового ручного експерименту щоразу.

**[Пропозиція інтерфейсу, НЕ затверджений UI]** У лабораторії показувати вихідну речовину → доступні методи → вимоги/умови → можливі результати та пояснення. Спершу навчати базових перетворень (очищення, відділення), згодом — керуванню умовами й оптимізації. Наприклад, для води можна вивчити електроліз; це не означає, що звичайний електролізер без підготовки підходить для морської води. Ні цей приклад, ні «водень як перша ціль» не є затвердженим рецептом чи порядком прогресії.

## 4. Антипатерн для Claude Code: магічний крафт складної машини

**[Рішення]** **Виготовлення обладнання й забезпечення його роботи — окремі етапи.** Складну установку спершу будують із конструкційних компонентів, а потім подають їй паливо, реагенти, енергію тощо для експлуатації. Не закладати витратне паливо в рецепт створення корпуса/машини як заміну її подальшому забезпеченню.

**Поганий приклад (НЕ реалізовувати):** `10 титану + 5 літію + 3 тритію → готовий працюючий реактор`.

**Кращий принцип:** створити реактор із відповідних деталей → встановити й підключити → забезпечувати потрібним паливом і системами під час експлуатації. Тритій та дейтерій — лише ілюстрація можливої пізньої енергетики; термоядерний реактор **не затверджений** як обов'язкова технологія.

## 5. Межі домовленостей і перевірка прототипом

**[Відкрито]** Детальна модель даних речовин (включно зі сумішами/чистотою), мінімальні класи тари, одиниці виміру, обмеження переносу, сумісність портів, UI лабораторії, рівні автоматизації, конкретні хімічні процеси й рецепти.

**[Відкрито]** Металургія, матеріалознавство й енергетика потребують **окремого обговорення**. Не переносити на них непогоджені деталі хімічної системи автоматично. Загальний принцип «виготовлення ≠ забезпечення роботи» стосується техніки широко.

**[Пропозиція для першого прототипу]** Одна рідина, два сумісні контейнери різної місткості, лабораторний аналіз та одна зрозуміла операція розділення; показати кількість вмісту, переливання, вимоги до машини, збереження відкритого способу й повторне використання через автоматичну подачу. Перевірити, чи новий гравець може пояснити причинно-наслідковий зв'язок без зовнішнього довідника.

## 6. Інструкція для Claude Code

- Не реалізовувати «речовина = предмет із власною іконкою й фіксованим стеком» для всіх газів і рідин.
- Не зливати `build/craft machine` і `operate/fuel machine` в одну подію або рецепт.
- Не перетворювати аналіз складу на автоматичне розблокування всіх способів використання.
- У прототипі обирати найпростішу перевірювану реалізацію, а не фізично повну симуляцію.
- Структуру коду, числовий баланс і точні API обирати після окремого технічного дизайну; цей документ фіксує геймдизайн, а не схему класів.
